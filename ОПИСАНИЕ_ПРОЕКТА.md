# Vozvrat — описание проекта простым языком

Этот документ объясняет, **что делает проект, как он устроен внутри и почему
разработчики приняли именно такие технические решения**. Текст рассчитан на
человека, который хочет разобраться в системе с нуля: и на программиста, который
будет её дорабатывать, и на менеджера, который хочет понять логику.

> Если коротко: это веб-приложение, которое помогает компании-продавцу
> автозапчастей принимать возвраты товара от клиентов и пересылать эти возвраты
> поставщикам. Главная «фишка» — система умеет **сама** создавать заявки на возврат
> из входящих писем с Excel-файлами, без ручного ввода.

---

## 1. Какую задачу решает проект

Представьте компанию (в коде она называется «Автопрагматик», домен `amx24`),
которая продаёт автозапчасти. Клиенты (другие фирмы — ООО и ИП) иногда хотят
вернуть бракованную или неподошедшую деталь. Дальше эту деталь нужно вернуть уже
**поставщику**, у которого её закупили.

Получается цепочка:

```
Клиент  →  Наша компания  →  Поставщик
(вернул)     (оформила)        (принял назад)
```

Раньше менеджеры вели всё это руками: получали письма, переписывали данные в
таблицы, отправляли поставщикам уведомления, выгружали данные в 1С. Проект
автоматизирует эту рутину:

- **Принимает заявки** тремя способами: вручную, из загруженного Excel и
  автоматически из почты.
- **Хранит** все возвраты в единой базе со статусами и историей.
- **Разграничивает доступ**: сотрудники видят всё, клиенты — только свои заявки.
- **Уведомляет поставщиков** письмом с фотографиями брака.
- **Выгружает данные** в 1С (через файл или по FTP).

## 2. На чём написан проект (стек) и почему

| Слой | Технология | Почему выбрали |
|------|-----------|----------------|
| Веб-сервер / API | **FastAPI** + Uvicorn | Современный, быстрый, асинхронный фреймворк на Python. Сам генерирует документацию и проверяет входные данные. |
| База данных | **PostgreSQL** | Надёжная реляционная СУБД. Здесь важны связи между таблицами (возврат → позиции → файлы) и точность денежных сумм. |
| Работа с БД | **SQLAlchemy 2.0 (async)** + asyncpg | ORM позволяет описывать таблицы как классы Python и не писать «голый» SQL. Асинхронный драйвер не блокирует сервер во время запросов. |
| Миграции | **Alembic** | Позволяет менять структуру БД пошагово и версионировать эти изменения (как git, только для схемы базы). |
| Проверка данных | **Pydantic v2** | Описывает, какие данные приходят и уходят, и автоматически их валидирует. |
| Внешний вид | **Jinja2 + HTMX + TailwindCSS** | Сервер отдаёт готовый HTML, HTMX обновляет куски страницы без полной перезагрузки, Tailwind — стили прямо в разметке. См. раздел 11 «Почему HTMX, а не React». |
| Вход в систему | **JWT в cookie** (python-jose + bcrypt) | Токен авторизации хранится в защищённой cookie, пароли — в виде bcrypt-хэшей. |
| Фоновые задачи | **APScheduler** | Раз в несколько минут сам проверяет почту. Встроен прямо в приложение — не нужен отдельный сервис типа Celery. |
| Работа с Excel | **openpyxl** | Чтение и запись `.xlsx`-файлов. |

**Главная идея стека:** взять «монолит» на одном языке (Python), который делает
всё сразу — и API, и HTML-страницы, и фоновую проверку почты. Для небольшой
компании это проще в разработке и дешевле в обслуживании, чем «модный» набор из
отдельного фронтенда на React, отдельного бэкенда и отдельного планировщика.

## 3. Архитектура в целом

Приложение разделено на **слои** — каждый отвечает за свою зону. Это классическая
схема, она помогает не запутаться, когда проект растёт.

```
Браузер (HTMX)
     │
     ▼
Nginx  ─────►  Uvicorn (FastAPI)
                   │
   ┌───────────────┼─────────────────┐
   ▼               ▼                 ▼
Routers        Services           Models
(маршруты)    (бизнес-логика)   (таблицы БД)
   │               │                 │
   └──────► PostgreSQL ◄─────────────┘
                   ▲
           APScheduler (раз в 5 мин лезет в почту по IMAP)
```

Что лежит в каждой папке внутри `app/`:

- **`models/`** — описание таблиц базы данных (что и как хранится).
- **`schemas/`** — описание данных, которые ходят через API (что приходит/уходит).
- **`routers/`** — «точки входа»: какие бывают адреса (URL) и что происходит при
  обращении к ним. Здесь же проверяются права доступа.
- **`services/`** — «мозг» приложения: вся сложная логика (разбор писем, отправка
  почты, работа с файлами). Роутеры стараются быть тонкими и зовут сервисы.
- **`templates/`** — HTML-шаблоны страниц (Jinja2).
- **`static/`** — стили и прочие статические файлы.

**Почему так разделили?** Чтобы каждый файл занимался одним делом. Например, если
нужно поменять способ разбора писем — правишь только `services/mail_import.py`, а
роутеры и модели не трогаешь. Это снижает риск что-то случайно сломать.

### Точка входа — `app/main.py`

Здесь собирается приложение: подключаются все роутеры, монтируется папка со
статикой и настраивается **жизненный цикл** (`lifespan`). При старте приложение:

1. создаёт папку для загрузок, если её нет;
2. запускает планировщик проверки почты;
3. сразу записывает «отметку жизни» (heartbeat), чтобы интерфейс не подумал, что
   планировщик мёртв, пока не настал первый тик.

При остановке — корректно гасит планировщик и закрывает соединения с БД.

## 4. Модель данных (что хранится в базе)

Это сердце системы. Все таблицы описаны как Python-классы в папке `models/`.

### Главные таблицы

**`refunds` (возвраты / заявки)** — центральная сущность. Одна строка = одна
заявка на возврат. Хранит: кто клиент, какой поставщик, статус, причину, откуда
пришла заявка (вручную/из письма), служебные данные письма (тема, отправитель,
UID письма) и т.д.

**`refund_items` (позиции возврата)** — что именно возвращают: артикул, бренд,
количество, цена, описание. Важная деталь: **цена хранится как `Numeric(16,2)`**,
а не как обычное дробное число. Это сделано специально — у `float` бывают ошибки
округления (0.1 + 0.2 ≠ 0.3), а для денег это недопустимо.

**`users` (пользователи)** — у каждого есть роль: `admin`, `staff` или `client`.
Пароль хранится только в виде bcrypt-хэша, никогда в открытом виде.

**`suppliers` (поставщики)** — название и email, куда слать уведомления.

**`file_attachments` (файлы)** — вложения к возврату: фото брака, Excel, PDF. У
файла есть флаг `is_internal` — внутренние файлы видят только сотрудники, клиент
их не получит.

**`messages` (сообщения/комментарии)** — переписка внутри карточки возврата. У
сообщения есть видимость: `all` (видят все) или `staff_only` (только сотрудники).

**`user_client_ids`** — у одного клиента может быть несколько «внешних» ID
(из систем заказчика). Эта таблица связывает их с аккаунтом. Нужна для автоимпорта
из почты — по такому ID система находит, какому клиенту принадлежит заявка.

**`mail_notifications` (уведомления о письмах)** — «журнал» всех входящих писем:
тема, отправитель, к какому возврату привязано, прочитано ли, и статус обработки
(`new`, `processed`, `skipped`, `failed`). Благодаря ему интерфейс показывает
«колокольчик» с новыми письмами и объясняет, почему то или иное письмо не
превратилось в заявку.

**`app_settings` (настройки)** — простая таблица «ключ-значение». Здесь хранятся
настройки SMTP, FTP, IMAP и переключатели функций. Почему в базе, а не в файле —
см. раздел 8.

### Как таблицы связаны

```
User (клиент) ──┐
                ├──< Refund >──┬──< RefundItem (позиции)
User (создал) ──┘             ├──< FileAttachment (файлы)
                              └──< Message (комментарии)
Supplier ─────────────────────┘
```

Связи настроены с правилом `cascade="all, delete-orphan"`: если удалить возврат,
вместе с ним автоматически удалятся его позиции, файлы и комментарии — чтобы не
оставался «мусор» в базе.

### Человеческий номер заявки

У возврата есть `id` (внутренний, для базы) и `display_id` — красивый номер вида
`#10001`, который видит человек. Второй генерируется как `10001 + максимальный id`.
Это сделано, чтобы номера выглядели солидно (начинались не с единицы) и были
понятны людям.

## 5. Авторизация: кто и что может делать

### Три роли

| Роль | Что доступно |
|------|--------------|
| `admin` | Всё: возвраты, поставщики, **пользователи**, настройки, статистика |
| `staff` (сотрудник) | Возвраты, поставщики, статистика — но **не** управление пользователями |
| `client` (клиент) | Только **свои** возвраты в личном кабинете |

### Как это работает технически

Логика в `services/auth.py`:

1. При входе проверяется пароль (через bcrypt) и выдаётся **JWT-токен** — это
   зашифрованная «справка», где написано «я пользователь №5, роль staff, годен до
   завтра».
2. Токен кладётся в **httponly-cookie**. «httponly» означает, что до него не может
   добраться JavaScript в браузере — это защита от кражи токена через XSS-атаки.
3. На каждый запрос функция `get_current_user` достаёт токен из cookie,
   расшифровывает его и находит пользователя в базе.
4. Функция `require_role("admin")` — это «вахтёр»: пускает дальше, только если
   роль совпадает, иначе возвращает ошибку 403 (нет доступа).

**Важный момент про клиента:** в запросах к базе добавляется фильтр
`Refund.client_user_id == user.id`. То есть клиент физически не может увидеть чужой
возврат, даже если подставит чужой номер в адресную строку — база просто ничего не
вернёт. Это надёжнее, чем прятать кнопки в интерфейсе.

## 6. Жизненный цикл возврата (статусы)

У каждой заявки есть статус. В коде (`models/refund.py`) их пять:

| Статус | Что значит | Цвет в интерфейсе |
|--------|-----------|-------------------|
| `received` | Получен (новая заявка) | синий |
| `approved` | Согласован | зелёный |
| `rejected` | Отказано | красный |
| `waiting_for_part` | Ожидаем деталь | жёлтый |
| `archive` | В архиве | серый |

Сотрудник меняет статус кнопками в карточке возврата. Каждому статусу заранее
заданы понятная русская подпись и цвет — это вынесено в словари `STATUS_LABELS` и
`STATUS_COLORS`, чтобы не дублировать эти подписи по всему коду.

> **Примечание для разработчика.** В файле `README.md` описана более старая,
> длинная цепочка статусов (`in_progress`, `sent_to_supplier`, `stock`,
> `completed`). Это устаревшая информация: в коде статусы уже **упрощены** до пяти
> перечисленных выше. При доработке ориентируйтесь на код, а не на README.

## 7. Главная фишка — автоимпорт заявок из почты

Это самая сложная и самая ценная часть проекта. Разберём подробно, потому что
именно здесь принято больше всего нетривиальных решений.

### Общая идея

Поставщики и клиенты присылают на почту письма с Excel-файлом (шаблон
`goodsReturnReport`), где перечислены товары к возврату. Система раз в несколько
минут заходит в почтовый ящик, читает новые письма, разбирает Excel и **сама
создаёт заявки**.

### Как запускается проверка (`main.py`)

Проверкой управляет планировщик **APScheduler**. Он встроен прямо в приложение и
раз в `MAIL_CHECK_INTERVAL_MINUTES` минут (по умолчанию 5) запускает задачу
`mail_check_job`.

**Проблема:** приложение в продакшене запускается в нескольких процессах (workers)
для скорости. Если бы планировщик стартовал в каждом — почта читалась бы по 2-3
раза, и появлялись бы дубли заявок.

**Решение:** перед стартом планировщик пытается захватить **файловую блокировку**
(`/tmp/vozvrat_scheduler.lock`). Захватить её может только один процесс — он и
становится «главным» по почте. Остальные видят, что замок занят, и спокойно
пропускают запуск. Простое и надёжное решение без внешних зависимостей.

### Почему IMAP запускается в отдельном потоке

Библиотека `imaplib` (работа с почтой) — **синхронная**: она «замораживает» поток,
пока ждёт ответа от почтового сервера. А FastAPI — асинхронный, ему нельзя
«замораживаться», иначе весь сайт повиснет для всех пользователей.

Поэтому всё общение с почтой вынесено в **пул потоков** (`run_in_executor`). Грубо
говоря: «сходи в почту в отдельном потоке и не мешай основному серверу
обслуживать людей». Плюс на сам IMAP стоит таймаут 30 секунд, а на всю задачу —
300 секунд, чтобы зависшее соединение не подвесило планировщик навсегда.

### Хитрость с поиском писем (важное решение)

Казалось бы, логично попросить почтовый сервер: «найди письма со словом *возврат*
в теме». Но в коде (`_build_imap_search_criteria`) этого специально **не делают** —
ищут просто все непрочитанные письма (`UNSEEN`).

Причина прямо описана в комментарии: поиск по теме на стороне IMAP-сервера надёжно
работает только для латиницы. Если в списке слов смешаны русское «возврат» и
английское «refund», сервер молча выкинет русское слово и будет искать только по
«refund» — и **ни одно русское письмо не найдётся**. Эта ошибка однажды тихо
сломала весь автоимпорт. Поэтому фильтрацию по ключевым словам делают **уже на
своей стороне** (в Python), где с русским языком всё в порядке.

Это хороший пример решения, принятого «по шрамам» — на основе реальной поломки.

### Многоуровневая фильтрация писем

Прежде чем создать заявку, письмо проходит проверки (всё настраивается):

1. **Отправитель** — есть ли он в «белом списке» разрешённых (`MAIL_ALLOWED_SENDERS`).
2. **Ключевые слова в теме** (`MAIL_SUBJECT_KEYWORDS`).
3. **Дата** — письмо должно прийти после момента, когда включили автосоздание
   (чтобы при первом запуске не «всосало» весь старый архив писем).
4. **Excel нашего шаблона** — в письме обязан быть `.xls/.xlsx` с колонкой
   «Артикул». Нет файла — нет заявки.

Если письмо не прошло фильтр, оно не теряется: в журнал `mail_notifications`
записывается причина отказа (например, «Отправитель не в списке разрешённых»), и
сотрудник видит это в интерфейсе.

### Защита от дублей и от «отравленной» транзакции

Каждое письмо имеет уникальный `UID`. Система помнит обработанные UID, поэтому одно
письмо не превратится в заявку дважды.

Очень аккуратно сделана обработка ошибок при пакетной обработке:

- Каждое письмо сохраняется в базу **отдельной транзакцией** (`commit` после
  каждого). Если одно письмо «битое» и вызвало ошибку — это не отменит заявки,
  созданные из других писем в той же пачке.
- При ошибке сначала делается `rollback`, потому что иначе вся сессия с базой
  «отравляется» и последующие письма тоже не сохранятся.
- Даже факт ошибки записывается в журнал (статус `failed` + текст ошибки),
  отдельной транзакцией — чтобы сотрудник увидел красный значок «Ошибка» и понял,
  что с письмом что-то не так.

Это признак зрелого кода: разработчик продумал, что пойдёт не так, и сделал так,
чтобы один сбой не ронял всю обработку.

### Один артикул — одна заявка

Если в Excel несколько строк (несколько товаров), система создаёт **отдельную
заявку на каждый товар**, а не одну общую. Это осознанное бизнес-решение (видно по
коду и истории коммитов): так каждой деталью удобнее управлять по отдельности —
у каждой свой статус, своя переписка, свой комплект файлов.

### Автосоздание клиентов и поставщиков

Когда из письма приходит заявка, система пытается понять, **чей** это возврат:

- **Клиента** ищет по внешнему ID (`client_ext_id`) или по email. Если не нашла —
  **создаёт новый аккаунт клиента** автоматически, со случайным паролем и
  служебным email вида `ext_client_123@imported.local`.
- **Поставщика** ищет по названию. Если нашла — привязывает по ID; если нет —
  просто запоминает название текстом в поле `supplier_name` (чтобы данные не
  потерялись, даже если такого поставщика ещё нет в справочнике).

Так система не «спотыкается» о незнакомых людей, а наоборот — сама наполняет
справочники.

## 8. Разбор Excel и текста письма — «defensive programming»

Файл `mail_import.py` показателен тем, как код **обороняется** от грязных входных
данных. Реальные письма и таблицы приходят в разном виде, и проект к этому готов.

### Гибкое чтение Excel (`try_parse_xls`)

- **Ищет строку с заголовками** в первых 20 строках файла (не всегда заголовок в
  первой строке — сверху бывает «шапка» с логотипом и т.п.).
- **Сопоставляет колонки по смыслу, а не по точному названию.** Например, артикул
  распознаётся и как «Артикул», и как «Article», и как «Арт.». Количество — «Кол-во»,
  «Количество», «qty». Это устойчиво к разным форматам от разных отправителей.
- **Чинит «битые» Excel.** Некоторые файлы (как раз тот самый `goodsReturnReport`)
  содержат некорректные служебные значения, на которых библиотека openpyxl падает
  с ошибкой. Код **аккуратно «латает» библиотеку на лету** (патчит проверку
  `NoneSet`), заменяя недопустимое значение на пустое вместо падения. Патч
  применяется один раз и защищён флагом, чтобы не накладываться повторно. Решение
  хитрое, но оно спасает от полной невозможности прочитать реальные файлы клиента.

### Разбор текста письма (когда Excel нет или мало данных)

Если данных в таблице не хватает, в ход идёт разбор **текста письма** несколькими
способами, по очереди (`parse_body_data`):

1. **Формат «Поле: Значение»** — ищет строки вида `Артикул: ABC123`,
   `Производитель: Bosch` через регулярные выражения.
2. **Двухсекционный формат** — когда сначала идёт список названий полей, потом, через
   пустую строку, список значений в том же порядке.
3. **Свободный текст** — если совсем ничего не структурировано, пытается выдернуть
   артикул как «код из латиницы и цифр» и количество по шаблону «12шт».

Это сделано потому, что люди пишут письма как попало, и система старается понять
максимум, а не требовать строгий формат.

### Защита от «расползания» данных

Отдельно стоит отметить мелкую, но важную защиту: короткие поля (артикул, бренд)
принудительно обрезаются до первой строки и до разумной длины. Без этого жадное
регулярное выражение могло бы «проглотить» весь текст письма и попытаться засунуть
его в колонку базы на 255 символов — и упасть. Такие детали показывают, что код
писали, набивая шишки на настоящих данных.

## 9. Настройки: часть в файле, часть в базе — почему так

Настройки живут в **двух местах**, и это сделано намеренно.

**`.env`-файл / переменные окружения** (`config.py`) — то, что задаётся один раз
при установке и обычно не меняется: адрес базы данных, секретный ключ для токенов,
параметры по умолчанию, лимиты на размер файлов.

**База данных** (таблица `app_settings`, сервис `settings_service.py`) — то, что
администратор должен иметь возможность поменять **прямо из интерфейса**, не залезая
на сервер: настройки SMTP (отправка почты), FTP (выгрузка в 1С), IMAP (входящая
почта), включён ли автоимпорт, тестовый режим отправки.

**Логика приоритета умная:** для почты значения из базы перекрывают значения из
`.env`. Если в базе поле пустое — берётся значение из `.env` как запасной вариант
(`get_mail_config`). Это даёт лучшее из двух миров: можно настроить через файл при
деплое, а можно потом удобно переопределить через админку.

**Зачем так?** Чтобы заказчику не нужно было звать программиста ради смены пароля
от почты. Он зайдёт в раздел «Настройки» и поменяет сам.

### «Сердцебиение» планировщика (heartbeat)

В настройках есть ключ `mail_last_check_at` — время последней проверки почты.
Планировщик записывает его при **каждом** запуске. Интерфейс смотрит на эту метку:
если она старше, чем два интервала проверки, значит планировщик, скорее всего,
умер, и сотруднику показывается предупреждение. Это простой способ отличить «почту
уже прочитали» от «проверка почты вообще не работает».

## 10. Работа с файлами

Логика в `services/file_service.py`.

- **Разрешены только безопасные типы:** `.xls, .xlsx, .pdf, .jpg, .jpeg, .png,
  .webp`. Всё остальное отклоняется.
- **Есть лимит на размер** (по умолчанию 20 МБ).
- **На диске файл получает случайное имя** (`uuid` + расширение), а настоящее имя
  (часто с русскими буквами) хранится отдельно в базе. Зачем: если положить русское
  имя прямо в путь на диске, на сервере с неправильной локалью открытие файла может
  упасть с ошибкой. Случайное латинское имя на диске эту проблему обходит. А
  пользователь всё равно видит оригинальное имя — оно берётся из базы.
- **Файлы каждого возврата лежат в своей папке** `uploads/refund_<id>/` — так
  удобнее и не возникает конфликтов имён.
- **Проверка доступа при скачивании:** клиенту не отдадут внутренний файл
  (`is_internal`) и не отдадут файл из чужого возврата.

Сами файлы хранятся **локально на диске сервера**, а не в облаке (S3 и т.п.). Для
одной компании на одном VPS это самое простое и дешёвое решение.

## 11. Интерфейс: почему HTMX, а не React

Фронтенд сделан на связке **Jinja2 (шаблоны) + HTMX + Tailwind**, и это сознательный
отказ от «тяжёлого» SPA-фреймворка вроде React/Vue.

**Как это работает.** Сервер отдаёт обычный HTML. Когда нужно обновить кусочек
страницы (например, таблицу возвратов после смены фильтра), HTMX делает запрос на
сервер и получает в ответ **готовый кусок HTML**, который вставляет на место — без
полной перезагрузки страницы. Видно по роутерам: рядом с «обычными» эндпоинтами
есть «partial»-эндпоинты вроде `/api/refunds/table`, которые возвращают не JSON, а
маленький HTML-фрагмент (`_table.html`, `_status_section.html` и т.п.).

**Почему так решили:**

- **Вся логика остаётся на Python**, на одном языке. Не нужно держать второй проект
  на JavaScript, отдельную сборку, отдельные зависимости.
- **Проще и быстрее в разработке** для команды, которая и так пишет бэкенд.
- **Меньше кода = меньше ошибок.** Для системы учёта возвратов не нужна сложная
  интерактивность как в Google Docs — HTMX полностью покрывает потребности.
- **Tailwind через CDN** — не нужен этап сборки CSS, стили пишутся прямо в разметке.

Это прагматичный выбор «достаточно хорошего» инструмента под реальную задачу, а не
под моду.

## 12. Интеграции с внешним миром

### Отправка писем поставщику (SMTP, `email_service.py`)

Из карточки возврата сотрудник может одной кнопкой отправить поставщику письмо со
списком товаров, причиной возврата и **фотографиями брака** во вложении. Текст
письма красиво форматируется. Полезные детали:

- **Тестовый режим.** Можно включить в настройках: тогда все письма уходят не
  реальным поставщикам, а на один тестовый адрес. Это страховка, чтобы при отладке
  случайно не завалить поставщиков письмами.
- **Принудительный IPv4.** Перед отправкой адрес сервера резолвится в IPv4. Это
  обходит частую проблему на VPS без IPv6 («Network is unreachable»).
- Поддержаны и обычный TLS (порт 587), и неявный SSL (порт 465).
- Отправка, как и почта, выполняется в отдельном потоке, чтобы не блокировать сервер.

Кроме писем поставщику, тот же сервис умеет слать уведомления сотруднику, которого
**упомянули в комментарии**, и отправлять **данные для входа** новому клиенту.

### Выгрузка в 1С (FTP / файл, `ftp_service.py`)

Данные о возвратах можно выгрузить для бухгалтерской системы 1С двумя путями:

- **Скачать файлом** прямо из интерфейса (`/api/refunds/export-1c`) — формат XLSX.
- **Загрузить на FTP-сервер** — формат CSV.

Важная техническая деталь в XLSX-выгрузке: колонки «Артикул» и «ID заказа»
**принудительно делаются текстовыми**. Иначе Excel превратил бы длинные числовые
артикулы в «научную запись» (вроде `1.23E+11`) и испортил бы данные. А CSV
сохраняется в кодировке `utf-8-sig` (с BOM), чтобы Windows и 1С правильно увидели
русские буквы.

Это снова примеры решений «из практики»: автор знал, на каких мелочах обычно
ломается обмен с 1С, и заранее их обошёл.

## 13. Миграции базы данных (Alembic)

Структура базы меняется со временем (добавляются поля, статусы, таблицы). Чтобы это
не превращалось в хаос, используется **Alembic**: каждое изменение схемы — это
отдельный пронумерованный файл-«миграция» в `alembic/versions/`.

По названиям файлов видна история развития проекта:

- `0001_initial_schema` — первая версия базы;
- `0003_add_app_settings...` — появились настройки в базе;
- `0007_..._mail_notifications` — добавился журнал писем;
- `0009_simplify_refund_statuses` — те самые упрощённые статусы;
- `0010_add_user_client_ids` — поддержка нескольких ID у клиента;
- `0013_add_rejected_and_waiting_for_part_statuses` — добавили статусы «Отказано» и
  «Ожидаем деталь»;
- `0014_add_is_internal_to_file_attachments` — появились внутренние файлы.

Команда `alembic upgrade head` приводит базу к актуальной версии. Так можно
безопасно обновлять боевую базу, не теряя данные.

## 14. Как это запускается в продакшене

Схема развёртывания (подробности — в `README.md`):

```
Интернет → Nginx (порт 443, HTTPS) → Uvicorn (порт 8000) → PostgreSQL
```

- **Nginx** стоит «спереди»: завершает HTTPS (сертификат Let's Encrypt), отдаёт
  статику напрямую (быстрее) и проксирует остальное в приложение.
- **Uvicorn** запускает само приложение FastAPI, обычно в 2 рабочих процесса.
- **systemd** следит, чтобы приложение автоматически перезапускалось при падении и
  стартовало при загрузке сервера.
- **PostgreSQL** крутится на той же машине.

Это типичная, проверенная временем схема для небольшого Python-приложения на одном
VPS. Ничего лишнего.

## 15. Общие принципы, которые видны в коде

Если выделить «характер» этого проекта одним списком:

1. **Монолит вместо микросервисов.** Один проект на Python делает всё. Для масштаба
   одной компании это проще, дешевле и надёжнее.
2. **Асинхронность везде, где есть ожидание.** Запросы к базе — асинхронные.
   Синхронные «тормозящие» вещи (почта, SMTP, FTP) вынесены в отдельные потоки,
   чтобы не блокировать сервер.
3. **Оборонительное программирование.** Код исходит из того, что входные данные
   будут грязными: письма кривые, Excel битый, локаль на сервере неправильная. Везде
   подстелена «соломка».
4. **Изоляция сбоев.** Одно плохое письмо не ломает обработку остальных. Ошибки
   логируются и показываются в интерфейсе, а не «съедаются» молча.
5. **Безопасность по умолчанию.** Пароли хэшируются, токен в httponly-cookie,
   доступ к чужим данным закрыт на уровне SQL-запроса, типы загружаемых файлов
   ограничены.
6. **Удобство для не-программиста.** Ключевые настройки вынесены в админку, есть
   тестовый режим почты, понятные русские подписи статусов и причин отказа.
7. **Решения «по шрамам».** Многие неочевидные куски (поиск писем без SUBJECT,
   патч openpyxl, текстовые колонки в выгрузке, IPv4 для SMTP) — это реакция на
   конкретные реальные поломки, а не теоретические «лучшие практики».

## 16. На что обратить внимание при доработке

Несколько честных замечаний для того, кто будет развивать проект:

- **README местами устарел** (особенно про статусы возвратов). Источник правды —
  код, а не README.
- **Дублирование `generate_display_id`.** Эта функция есть и в `routers/refunds.py`,
  и в `services/mail_import.py`. При доработке логики номеров нужно помнить про оба
  места.
- **Генерация `display_id` через `max(id)+10001`** не защищена от гонок: при двух
  одновременных созданиях теоретически возможен конфликт. На текущих нагрузках это
  не проблема, но при росте стоит перейти на последовательность (sequence) в базе.
- **Патчи openpyxl** в двух местах слегка отличаются — при доработке разбора Excel
  имеет смысл свести их в одну общую функцию.
- **Файлы хранятся локально на диске.** Это нормально для одного сервера, но при
  переезде на несколько серверов или в контейнеры понадобится общее хранилище
  (например, S3-совместимое).
